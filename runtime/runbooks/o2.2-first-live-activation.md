## 1. Seed the source set

```bash
# Step 1 — review what would be created
npm run seed:market-sources:dry-run

# Step 2 — create (inactive by default — safe)

# Expected output:
#   [seed-market-sources] seeds=20 dryRun=false activate=false
#   [seed-market-sources] total=20 created=20 alreadyExisted=0 errors=0
#   [seed-market-sources] Done. New rows are isActive=false. Next:
#     npm run verify:market-sources -- --activate
```

The seed creates ~20 MarketSource rows (17 P&Z + 2 city-council + 1 utility-board) covering the Des Moines metro per [o2.1-first-bloodstream.md §2](o2.1-first-bloodstream.md). **All new rows are `isActive=false`** — they will not be picked up by the runner until verification activates them.

**Idempotency**: re-running `npm run seed:market-sources` is safe. Sources are matched by `(jurisdiction, sourceType, name)`; existing rows are skipped. The seed never mutates existing data — it only inserts what's missing.

## 2. Verify the source URLs

The seed file uses best-guess CivicPlus `/AgendaCenter` URLs. Some will be wrong — cities rename pages, switch stacks, or use subdomains. The verify script catches that:

```bash
# Dry-run: report only, no DB writes
npm run verify:market-sources:dry-run

# Live: flip recommended=activate sources to isActive=true,
#       flip recommended=remove sources to publishStatus=OPERATOR_REVIEW
npm run verify:market-sources -- --activate --quarantine
```

Output shape:
```
[verify-market-sources] verifying 20 source(s) (concurrency=4, timeout=12000ms)
[verify-market-sources] results:
  [ACTIVATE   ] Ankeny               Ankeny — Planning & Zoning Commission           HTTP 200 CIVICPLUS_AGENDA_CENTER links=42
  [INVESTIGATE] Polk City            Polk City — Planning & Zoning Commission        HTTP 200 GENERIC_HTML links=1
  [REMOVE     ] Mitchellville        Mitchellville — Planning & Zoning Commission    UNREACHABLE
                  └─ DNS lookup failed
[verify-market-sources] summary: activate=14  investigate=3  remove=3
[verify-market-sources] writes: activated=14  quarantined=3
```

Recommendations:
- **activate** — reachable + known stack signature detected (CivicPlus AgendaCenter / CivicClerk / Granicus). Safe to auto-flip `isActive=true`.
- **investigate** — reachable but no stack signature OR few candidate links. Operator inspects the URL manually (open the page in a browser); the right URL might be `/Pages/AgendaCenter` or `/Government/Boards/PlanningCommission` or a sub-path. Update the URL via the SourcesPanel and re-verify.
- **remove** — unreachable, 4xx/5xx, or wrong content-type. Auto-quarantined to `OPERATOR_REVIEW` if `--quarantine` was passed — the runner will skip it. Operator decides: find the real URL and PATCH, or delete the row.

After `--activate --quarantine`, only verified-and-reachable sources are live. Anything quarantined is excluded from `selectDueSources` (PR4 predicate requires `publishStatus='HEALTHY'`).

## 8. Rollback path

Activation is fully reversible — no destructive operations, no migrations, no service restarts required to halt the engine.

### Hard stop (stop all autonomous ingestion immediately)

```bash
docker compose -p neuroglitch-staging stop cron
```

The cron container stops; in-flight `tsx scripts/run-cycle.ts` children finish their current cycle and exit. No new cycles fire. Already-persisted `MarketSignal` / `Project` rows remain (no rollback needed — they were never invalid, just unwanted).

### Soft stop (stop ingestion but keep cron container running for health-check)

```bash
# Mark all PR5-seeded sources as OPERATOR_REVIEW — runner skips them
docker compose -p neuroglitch-staging exec app tsx -e '
  import {prisma} from "@/lib/prisma";
  prisma.marketSource.updateMany({
    where: { /* whatever criteria — e.g. specific sourceType or createdAt window */ },
    data: { publishStatus: "OPERATOR_REVIEW" },
  }).then((r) => console.log("quarantined", r.count));
'
```

The municipal-agenda-ingestion cycle still fires hourly but `selectDueSources` returns 0 rows. Health-check keeps ticking. Reverse later via the SourcesPanel "Mark healthy" button.

### Full revert (undo PR5 entirely)

```bash
# 1. Stop cron
docker compose -p neuroglitch-staging stop cron

# 2. Delete all PR5-seeded sources (only the ones with the seed signature)
docker compose -p neuroglitch-staging exec app tsx -e '
  import {prisma} from "@/lib/prisma";
  import {DES_MOINES_METRO_SEEDS} from "@/lib/services/marketIntelligence/seedSources";
  Promise.all(DES_MOINES_METRO_SEEDS.map((s) =>
    prisma.marketSource.deleteMany({
      where: { jurisdiction: s.jurisdiction, sourceType: s.sourceType, name: s.name },
    })
  )).then((rs) => console.log("deleted", rs.reduce((a, r) => a + r.count, 0)));
'

# 3. Optionally clean orphaned MarketSourceDoc / MarketSignal rows
#    (cascade-delete on sourceId already handles MarketSourceDoc; signals
#    with sourceDocId become orphaned with null FK — operator-driven)
```

Schema is untouched — there are no PR5 migrations.

## 9. Known issues + tuning recommendations

### Expected initially (NORMAL — not a bug)

- **Imperfect classification.** First-week heuristics are tuned conservatively (`BASE_SCORE=0.35`, ceremonial weights -0.30 to -0.65). Some marginal signals will be MEDIUM-banded when they should be LOW; some non-substantive items will slip through. Inspect `MarketSignal.heuristicsJson` for the factor breakdown.
- **Noisy suppression tuning.** Some headlines will be over-suppressed (e.g. "Public Notice of Hearing for Comprehensive Plan Amendment" — the CEREMONIAL_PATTERN + ADMINISTRATIVE_NOTICE keywords fire, but it's actually a substantive item). Operator can inspect via DB query: `SELECT headline, heuristicsJson FROM MarketSignal WHERE heuristicsClassification = 'SUPPRESSED' LIMIT 20` — but PR3 NEVER PERSISTS SUPPRESSED ROWS. To audit suppression: temporarily set `--skipHeuristics` via the scrape route to see what would have been dropped, OR add a debug-only persistence path in a follow-up PR.
- **Cadence-learning instability.** Sources start with `cadenceConfidence=null`; first 1-4 doc dates yield LOW; >5 yields MEDIUM. Don't tune `selectDueSources` parameters until the sources have soaked for 30+ days.
- **Sparse project formation.** MI-6 project-aggregation requires multi-signal patterns to confidently form projects. Expect singleton signals dominant for the first 1-2 weeks; project aggregates accrue as recurrence patterns appear.

### Tuning levers (do NOT touch in first week — let the system soak)

- **Heuristic weights** in `lib/services/marketIntelligence/signalHeuristics.ts` — bumping `HEURISTICS_VERSION` is a versioning event.
- **Cadence parameters** in `lib/services/marketIntelligence/sourceCadence.ts` — `DORMANCY_RUN_THRESHOLD`, `SAFETY_FLOOR_DAYS`.
- **Sources-per-cycle cap** in `lib/runners/municipalAgendaIngestion.ts` (currently 10).
- **Per-source `minRelevanceScore`** via SourcesPanel — operator can raise to 70+ for noisy sources.
- **Per-source `prefilterMode`** via SourcesPanel — flip to `large` or `always` to engage Ollama prefilter on bloated agendas.

### Failure modes

| Symptom | Likely cause | Action |
|---|---|---|
| `[cron] schedule_load_failed` and restart loop | Malformed `schedule.json` | Validate JSON; fix; restart `cron`. |
| Cron ticks but `runner_cycles_total` doesn't move | Runner not registered | Verify `scripts/run-cycle.ts` imports the runner. `tsx scripts/run-cycle.ts --list` should show `municipal-agenda-ingestion`. |
| Runner cycles but `signalsCreated=0` consistently | All sources STALE_PUBLISH, all URLs dead, or sidecar unreachable | Check `ActivationSummary` "Active sources" vs "Stale / review" counts. Inspect `[scrape-bridge]` audit lines for upstream errors. Re-run `verify:market-sources` to refresh recommendations. |
| Sidecar 5xx errors on every scrape | Sidecar misconfigured or rate-limited | `docker compose logs sidecar`. The sidecar's Claude API key + concurrency settings live in its env. |
| `signalsSuppressedHeuristics` is 100% of throughput (everything dropped) | Heuristic weights too aggressive OR all sources returning ceremonial-only content | Inspect a sample: `npx tsx scripts/run-cycle.ts --runner=municipal-agenda-ingestion --window-key=debug-1 --trigger=manual` and tail logs. If heuristics are wrong, tune in a follow-up PR. If sources are wrong, re-verify. |
| One source consistently throws upstream | URL retired or CivicPlus session-required | `verify:market-sources --source=<id>` to confirm. PATCH the source URL or quarantine. |
| Cron container healthcheck failing | Loop wedged | `docker compose restart cron`. If recurs, capture `docker logs cron` and inspect for unhandled rejections. |

## 11. Forecast activation (PR7)

After the ingestion runner has soaked for one week and produced real signals + projects, the **forecast-daily** runner becomes available. It runs at 08:00 UTC daily (≈ 03:00 CDT / 02:00 CST) and recomputes emergence forecasts for active Projects + Parcels.

### Soft gating

The runner is soft-gated by [`checkForecastGates()`](../../lib/services/emergenceProbability/forecastGates.ts). Each cycle calls it first; if any gate fails, the cycle no-ops + audits + returns. The four gates:

| Gate | Threshold | Reason |
|---|---|---|
| `min_market_signals` | ≥ 100 MarketSignal rows | Forecast inputs need real volume. |
| `min_projects` | ≥ 5 active Project rows | Without subjects, forecast has nothing to score. |
| `cadence_movement` | ≥ 3 sources with published cadence estimate | Confirms ingestion runtime is steady-state. |
| `no_recent_runner_errors` | 0 runner failures in prior 72h | Stop forecasting on top of broken ingestion. |

### Pre-flight gate check

Operator-runnable any time:

```bash
npm run forecast:gate-check
# exit 0 = gates pass; exit 1 = at least one gate fails
```

Sample failing output:

```
[forecast-gate-check] FAIL — 4 gate(s)
  [PASS] min_market_signals: 247 MarketSignal rows (need ≥ 100)
  [PASS] min_projects: 12 active Project rows (need ≥ 5)
  [FAIL] cadence_movement: 1 sources have published cadence estimate (need ≥ 3)
  [PASS] no_recent_runner_errors: 0 runner cycle(s) failed in prior 72h (need 0)
```

### Activation procedure

1. Add the schedule entry (already present in `runtime/cron/schedule.json` post-PR7):
   ```json
   { "cron": "0 8 * * *", "runner": "forecast-daily", "trigger": "scheduled" }
   ```
2. Restart cron container so the schedule loads:
   ```bash
   docker compose -p neuroglitch-staging restart cron
   ```
3. Run `npm run forecast:gate-check` — expect PASS.
4. Optionally smoke-test by triggering the runner once on-demand:
   ```bash
   docker compose -p neuroglitch-staging exec app tsx scripts/run-cycle.ts \
     --runner=forecast-daily --window-key=smoke-$(date +%Y%m%d-%H%M%S) --trigger=manual
   ```
5. Watch the next 08:00 UTC tick in `docker compose logs -f cron`.

### What you should see

| Time after activation | Expected |
|---|---|
| Next 08:00 UTC | `[cron]` `spawn forecast-daily`; `runner_cycle{runner=forecast-daily, status=ok}` increments. |
| Per cycle (first run) | All N active Projects + Parcels get a fresh `ForecastSnapshot`. `EmergenceScore` row upserted for each. `ProbabilityTrend` row written for any subject whose score changed by ≥ 0.005. |
| Per cycle (subsequent) | Most subjects produce `skipped_unchanged` (heuristic outputs steady). New `MarketSignal` arrivals between cycles will move scores; those subjects re-snapshot. |
| Per cycle | Per-subject `EmergenceTrajectory` upserted. Any state change emits a structured `[emergence-forecast]` `trajectory_shift` audit line with from/to/scoreDelta/topContributors. |

### Forecast operator-visible surfaces

- **Activation Report page** (`/market-intelligence/activation`) — PR7 added a "Forecast activity" section: 24h/7d snapshots, trajectory shifts, HIGH-emergence project + parcel counts, last cycle status, biggest 24h shifts, top HIGH-emergence projects.
- **CLI**: `npm run activation:report` now includes a FORECAST ACTIVITY section.
- **Audit stream** (Loki): grep `[emergence-forecast]` — every `persist_forecast` + `trajectory_shift` + `gates_not_met` audit.
- **Prometheus gauges**: `neuroglitch_forecast_high_emergence_count{subject_kind}` updates each cycle.
- **Prometheus counters**: `neuroglitch_forecast_recomputed_total{subject_kind, decision}`, `neuroglitch_forecast_failures_total{subject_kind}`, `neuroglitch_forecast_trajectory_shifts_total{from, to}`.

### Forecast rollback

Same hard-stop as the ingestion runner:

```bash
# Stop cron — both runners halt
docker compose -p neuroglitch-staging stop cron

# Or: remove just the forecast entry from schedule.json + restart cron
# (ingestion keeps running)
```

`ForecastSnapshot` is append-only — rollback never destroys history. Operator overrides remain via `overrideForecast` even when the runner is off.

### Forecast failure modes

| Symptom | Likely cause | Action |
|---|---|---|
| `gates_not_met` every cycle | Pre-conditions not met (ingestion still warming) | Wait for ingestion soak; verify via `npm run forecast:gate-check`. |
| Cycle succeeds but `subjectsForecasted=0` | All subjects produced `skipped_unchanged` (steady scores) | Normal at steady state. New signals will trigger movement on next cycle. |
| Single subject keeps throwing | `buildForecastSubjectContext` returns null (subject deleted) OR a downstream MI-8 scorer has a NaN / unexpected input | Inspect via stdout warnings. `recordForecastFailure{subject_kind}` increments per failure. One subject's failure does not poison the cycle. |
| HIGH-emergence count drops sharply | Could be real (decay across the region) OR a heuristics regression | Check `[emergence-forecast]` audit for `trajectory_shift` entries; correlate with recent code changes. Manual `overrideForecast` is available for individual subjects. |
| Cycle takes > 50 min (approaches `maxDurationSeconds`) | Too many active subjects for the lease window | Lower `FORECAST_DAILY_PROJECT_LIMIT` / `FORECAST_DAILY_PARCEL_LIMIT` in `forecastDaily.ts`. Future PR can shard subjects across multiple cycles. |

## 12. Alert evaluation (PR8)

PR8 introduces the third autonomous cycle: hourly **alert-eval**. Once the forecast loop is steady, alert-eval continuously asks "what deserves human attention right now?" and writes AlertEvent rows via the existing MI-10 infrastructure.

### Detector roster (deterministic — no AI)

| Trigger kind | Default severity | Cooldown | Fires when |
|---|---|---|---|
| `NEW_HIGH_EMERGENCE` | IMPORTANT | 24h | `ProbabilityTrend` shows score crossed ≥ 0.70 from below within last 24h |
| `TRAJECTORY_SHIFT_TO_ACCELERATING` | IMPORTANT (IGNITING) / WATCH (ACCELERATING) | 24h | `EmergenceTrajectory` entered IGNITING or ACCELERATING within window |
| `TRAJECTORY_SHIFT_TO_DECAYING` | WATCH | 48h | trajectory entered DECAYING/STALLED/DORMANT from non-decay state |
| `STALE_RECOVERY` | WATCH | 48h | trajectory previously DORMANT/STALLED, now EMERGING/ACCELERATING/IGNITING |
| `RECURRING_DEVELOPER` | WATCH | 7d | same actor (developer/owner name) appears across ≥ 3 distinct source docs in last 7d |
| `GOVERNANCE_BURST` | IMPORTANT | 24h | ≥ 3 governance-subtype signals from same jurisdiction in 24h |
| `FORECAST_OVERRIDE` | INFO | 24h | operator overrode a forecast (sanity surface) |
| `SOURCE_DEGRADATION` | INFO | 7d | MarketSource newly flipped to STALE_PUBLISH |
| `SUPPRESSION_ANOMALY` | WATCH | 24h | 24h SUPPRESSED count > 2× rolling 7d avg AND > 50 (absolute floor) |

### Severity normalization (PR8 contract)

Operator-facing bands are exactly four: **INFO / WATCH / IMPORTANT / CRITICAL**.

PR8 introduces `normalizeSeverity()` in [lib/services/operatorWorkspace/alertSeverityNormalize.ts](../../lib/services/operatorWorkspace/alertSeverityNormalize.ts) which maps the legacy MI-10 enum (`INFO / WATCH / ATTENTION / URGENT`) to the new bands without breaking existing AlertEvent rows or rules:

| Legacy | Normalized |
|---|---|
| INFO | INFO |
| WATCH | WATCH |
| ATTENTION | IMPORTANT |
| URGENT | CRITICAL |

The runner emits the normalized bands directly into `AlertEvent.severity` (the column is `String` — no schema change). Operator-rule-driven AlertEvents continue to use the legacy enum; the activation report normalizes both at read time.

### Cooldown + fingerprinting

Every persisted AlertEvent carries a fingerprint in `payloadJson`:

```
fingerprint = {triggerKind}|{subjectKind}|{subjectId}
e.g. "NEW_HIGH_EMERGENCE|PROJECT|ck_abc"
```

`persistRunnerAlert()` queries `AlertEvent.payloadJson` (Prisma `contains`) for the same fingerprint in the cooldown window. If a match exists, the candidate is suppressed and counted in `neuroglitch_alerts_suppressed_total{reason=cooldown}`.

Replay safety: re-running the same hour's alert-eval cycle is a no-op because all candidates collide with their own just-written fingerprints.

### Explainability flow

Every AlertEvent persisted by PR8 carries:
- `AlertExplanation` rows — one per factor (existing MI-10 table).
- `payloadJson` enriched with:
  - `runnerTriggerKind` (e.g. `"GOVERNANCE_BURST"`)
  - `fingerprint`
  - `runnerAlertsVersion` (`"v1"`)
  - `priorHistory`: `{priorAlertCount30d, lastAlertAt, priorTriggerKindCounts}` — operator sees "this subject has fired 4 alerts in 30 days, last 6h ago, 3 of those were RECURRING_DEVELOPER"
  - per-detector context (e.g. previousState/currentState for trajectory shifts, sampleSignalIds for governance bursts)

Operators can read the full breakdown from the activation report page, or query `AlertExplanation` joined to `AlertEvent.id` for analytical surfaces.

### Activation procedure

1. Schedule entry already present in `runtime/cron/schedule.json` post-PR8:
   ```json
   { "cron": "30 * * * *", "runner": "alert-eval", "trigger": "scheduled" }
   ```
   (Minute 30 avoids colliding with hourly municipal-agenda-ingestion at minute 0.)
2. Restart cron container: `docker compose -p neuroglitch-staging restart cron`.
3. Verify the runner is registered: `tsx scripts/run-cycle.ts --list` — expect `alert-eval` in the list.
4. Optionally smoke-test on demand:
   ```bash
   docker compose -p neuroglitch-staging exec app tsx scripts/run-cycle.ts \
     --runner=alert-eval --window-key=smoke-$(date +%Y%m%d-%H%M%S) --trigger=manual
   ```
5. Tail `[workspace]` audits in the app container logs for `record_alert_event` lines.

| Time after activation | Expected |

### Rollback

Same as forecast runner — non-destructive:

```bash
docker compose -p neuroglitch-staging stop cron
# OR: remove just the alert-eval entry from schedule.json + restart cron
```

`AlertEvent` is append-only. Operator-reviewed status (ACKNOWLEDGED / DISMISSED / ESCALATED / SUPPRESSED) is preserved when the runner is off.

### Failure modes

| Symptom | Likely cause | Action |
|---|---|---|
| Cycle succeeds but `alerts persisted = 0` every time | Either (a) nothing in the DB triggers any detector, or (b) every candidate is suppressed by cooldown | Inspect `neuroglitch_alerts_candidates_total` vs `_suppressed_total`. If candidates > 0 and all suppressed, cooldown is working as intended. If candidates = 0, ingestion + forecast aren't producing enough state changes — check earlier runners. |
| One detector throws | Detector caught + logged; cycle continues | `neuroglitch_alerts_suppressed_total{reason=detector_error}` increments. Stdout warning identifies the trigger kind. Fix in a follow-up PR. |
| Operator inbox floods with alerts | Cooldown too short OR detectors over-firing | Tune per-detector `cooldownMinutes` in `runnerAlerts.ts` `DETECTOR_CONFIG`. Bump RUNNER_ALERTS_VERSION when changing. |
| Unread-count gauge stuck at high number | Operators haven't reviewed alerts; or review workflow broken | Use existing MI-10 `reviewAlertEvent()` via UI. Older alerts can be batch-acknowledged via direct DB if needed. |
