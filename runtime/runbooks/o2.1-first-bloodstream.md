**Phase:** O2.1 — Activate the first recurring municipal-agenda ingestion pipeline.
**Status:** Design (this document). Implementation lands in O2.2.
**Companion docs:** [o2-runtime-design.md](o2-runtime-design.md) (the runner framework + 6-cycle plan).
**Authored to unblock:** `neuroglitch_ingestion_processed_total = 0` on the [intelligence-throughput dashboard](../observability/grafana/dashboards/intelligence-throughput.json).

## 0. How this fits the existing O2 plan

[o2-runtime-design.md](o2-runtime-design.md) sequences O2 as: cron container (O2.1) → forecast-daily (O2.2) → alert-eval (O2.3) → outcome-detect (O2.4) → calibration + briefings (O2.5) → backfills (O2.6).

That sequence implicitly assumes Projects and MarketSignals are already flowing in. They are not. Today the cognition substrate is healthy but starved — no recurring ingestion runner exists. **All seven cycles in the original O2 plan score, calibrate, and brief on data that no one is producing.**

This document inserts a **municipal-agenda ingestion runner** as the first activated cycle. Concretely:

- Treat `o2-runtime-design.md`'s O2.1 (cron container) as a prerequisite of *this* O2.1, not a substitute.
- Ship the cron container + this ingestion runner together as the first two PRs.
- Defer forecast-daily until ingestion has produced ≥ 100 MarketSignal rows on staging (≈ 1–2 weeks of soak).

The original O2 sequence becomes: cron container → **municipal-agenda-ingestion** → forecast-daily → alert-eval → outcome-detect → calibration + briefings.

### 1.3 The actual `processed:0` blocker

There are **two** problems:

1. **No recurring runner.** Today scrapes only happen when an operator clicks "Scrape" in the UI ([SourcesPanel.tsx](../../app/market-intelligence/SourcesPanel.tsx)) — meaning the platform processes nothing while no one is logged in.
2. **Even when scrapes do happen, the live-ingestion chain never fires.** [app/api/market-intelligence/sources/[id]/scrape/route.ts](../../app/api/market-intelligence/sources/[id]/scrape/route.ts) calls `persistSidecarPayload()` (lines 176–185), which writes raw `MarketSignal` / `MarketLead` / `RelationshipEdge` rows. **It never subsequently calls `processNewMarketSignal()` etc. from [lib/services/liveIngestion/](../../lib/services/liveIngestion).** Rows land in the DB cold — no ProjectSignal attach, no ProjectProbabilitySnapshot, no `neuroglitch_ingestion_processed_total{}` increment.

Fixing only #1 (a runner that calls the existing scrape pipeline on a schedule) leaves `processed:0`. **The runner body must also close the bridge by calling liveIngestion on each created row.**

## 2. Choice of first-source canonical path

**Decision: planning/zoning agendas via CivicPlus AgendaCenter (and CivicClerk fallback). Not utility agendas.**

The user prompt names "utility + municipal agendas" as the first source class. I am narrowing further within that class to **municipal P&Z agendas** specifically, for these reasons:

| Criterion | P&Z agendas | Utility-board agendas |
|---|---|---|
| Reliability of source | High — CivicPlus AgendaCenter is the dominant Iowa stack; standardized URL patterns; well-mapped by [routers/discover.py](../../sidecar/routers/discover.py). | Medium — utility districts (DSM Water Works, Central Iowa Water Works, MWA) use heterogeneous publishing (SharePoint, custom CMS, sometimes minutes only as PDF email blast). |
| Structured access | High — listing pages + dated PDFs + CivicClerk JSON API fallback already coded. | Low — most utility boards publish board packets without consistent naming or dating. Per-district custom parsing. |
| Repeatability | High — monthly P&Z cadence is universal (one or two meetings/month). | Variable — utility boards run monthly to quarterly with frequent recess. |
| Parsing quality | High — Claude prompt in [routers/market.py](../../sidecar/routers/market.py) already enumerates P&Z subtypes (REZONING, PLAT, SITE_PLAN, SUP_CUP, VARIANCE, COMPREHENSIVE_PLAN, ANNEXATION, TIF). | Medium — sewer/water/utility expansion is currently mapped to OTHER. Needs prompt extension (small task). |
| Emergence density | High — every rezoning, site plan, plat is a forward-looking development signal. | High when present, but sparse. Most utility-board items are operational (rate hearings, billing approvals). |
| Replayability | High — CivicPlus PDFs are stable URLs with persistent file IDs. | Medium — SharePoint links rotate. |
| Existing tooling completeness | ~95% (discovery + crawl + parse + persist all built; just need scheduling + ingestion bridge). | ~40% (would need per-district adapters). |

**Recommendation:** ship P&Z agendas first. Add utility-board sources as a *manual seeding* exercise once the runner is proven on P&Z — they ride the same runner and the same pipeline, they just need their URLs configured in MarketSource rows. **No separate runner.** "Utility agendas" is a source-set configuration question, not an architecture question.

Concrete starting set (≤ 25 sources to seed): Des Moines P&Z, Polk County P&Z, Ankeny P&Z, Urbandale P&Z, West Des Moines P&Z, Waukee P&Z, Clive P&Z, Johnston P&Z, Altoona P&Z, Pleasant Hill P&Z, Norwalk P&Z, Indianola P&Z, Bondurant P&Z, Grimes P&Z, Polk City P&Z, Mitchellville P&Z, Carlisle P&Z. Then 4–8 corresponding city council pages (council often ratifies P&Z items, providing a second-touch signal). Plus 2–3 utility-board pages (DSM Water Works, Central Iowa Water Works) seeded but flagged `prefilterMode = "always"` to suppress operational-item noise.

## 3. Runner design — `municipal-agenda-ingestion`

### 3.1 Identity

```
name:                "municipal-agenda-ingestion"
windowGranularity:   "hourly"
leaseSeconds:        900          # 15-min lease
maxDurationSeconds:  3300         # 55-min ceiling; never overlap the next hour's window
retryOnFailure:      false        # operator-initiated retry via --window-key=<recovery-key>
```

Hourly cadence is *not* hourly scraping. The runner wakes hourly, asks "what's due right now?" and acts only on sources whose `nextExpectedAt <= now()`. Most hours, the runner is a 1-second no-op that updates a heartbeat metric. This is intentional: it lets us push to a tighter cadence later without re-architecting.

### 3.2 Body shape (informal pseudocode — actual TS in O2.2)

```typescript
registerRunner<MunicipalAgendaResult>({
  name: "municipal-agenda-ingestion",
  windowGranularity: "hourly",
  leaseSeconds: 900,
  maxDurationSeconds: 3300,
  retryOnFailure: false,
  body: async (ctx) => {
    const due = await selectDueSources({ now: ctx.windowStart, limit: 10 });
    const summary = initSummary();

    for (const source of due) {
      if (!(await ctx.heartbeat())) throw new Error("lease preempted");

      try {
        // 1. Reuse the existing scrape pipeline (don't refactor it yet).
        //    Extract the body of app/api/.../scrape/route.ts into a callable
        //    function: scrapeOneSource({sourceId, ...}) → ScrapeResult.
        const scrape = await scrapeOneSource({ sourceId: source.id });

        // 2. Bridge: invoke live-ingestion on every newly created row.
        //    THIS IS THE STEP THE HTTP ROUTE OMITS.
        for (const signalId of scrape.createdSignalIds) {
          await processNewMarketSignal(signalId, { runnerId: ctx.runnerId });
        }
        for (const leadId of scrape.createdLeadIds) {
          await processNewMarketLead(leadId, { runnerId: ctx.runnerId });
        }
        for (const edgeId of scrape.createdEdgeIds) {
          await processNewRelationshipEdge(edgeId, { runnerId: ctx.runnerId });
        }

        // 3. Update cadence learning on the source.
        await updateSourceCadence(source.id, scrape);

        summary.sourcesScraped++;
        summary.docsScanned          += scrape.docsScanned;
        summary.signalsCreated       += scrape.signalsCreated;
        summary.leadsCreated         += scrape.leadsCreated;
        summary.relationshipsCreated += scrape.relationshipsCreated;
        summary.signalsIngested      += scrape.createdSignalIds.length;
        summary.totalCostUsd         += scrape.totalCostUsd;
      } catch (err) {
        summary.errors.push({ sourceId: source.id, message: String(err) });
        await recordSourceFailure(source.id, err);
        // continue to next source — one source's failure must not poison the cycle
      }
    }

    return summary;
  },
});
```

### 3.3 `selectDueSources` — the heart of the cadence governance

```sql
SELECT * FROM MarketSource
WHERE isActive = true
  AND sourceType IN ('planning_commission', 'city_council', 'utility_board')
  AND (
    nextExpectedAt IS NULL                            -- never scraped → run now
    OR nextExpectedAt <= :now
    OR (lastScannedAt IS NOT NULL                     -- safety floor:
        AND lastScannedAt < :now - INTERVAL '7 days') -- never let a source go > 7d
  )
ORDER BY
  CASE WHEN nextExpectedAt IS NULL THEN 0 ELSE 1 END, -- new sources first
  COALESCE(nextExpectedAt, lastScannedAt) ASC NULLS FIRST
LIMIT :limit
```

Per cycle: cap at 10 sources. With ~25 seeded sources and a typical publish cadence of 14–30 days, the runner touches roughly 1–3 sources per day at steady state. Cost ceiling: 10 sources × max ~5 new docs each × ~$0.10/doc = $5/cycle hard cap. In practice: $0.50–$2/day.

### 3.4 `updateSourceCadence` — smart polling

The MarketSource model already has fields for this; nothing exists to update them.

```typescript
function updateSourceCadence(sourceId: string, scrape: ScrapeResult): Promise<void> {
  // 1. If new docs were found, append documentDate to a per-source rolling
  //    sample of the last 20 doc dates (kept in a small per-source JSON blob
  //    on a new MarketSourceCadenceSample table — see §7.2).
  // 2. Recompute median Δ between consecutive doc dates.
  // 3. publishCadenceDays = median(Δ); cadenceConfidence = LOW (<5) | MEDIUM (5-15) | HIGH (>15).
  // 4. nextExpectedAt = lastDocSeenAt + publishCadenceDays - 1 day (lead by one day).
  // 5. If scrape found zero new docs AND nextExpectedAt has passed, push out
  //    by min(7d, 0.5 * publishCadenceDays) — exponential-backoff-lite, capped at weekly.
  // 6. If three consecutive runs find zero docs past the expected date, mark
  //    source as STALE_PUBLISH (new field) and require operator review.
}
```

This is the only logic worth designing carefully — everything else is wiring. The fields exist; the math is small.

## 5. Cadence governance

| Concern | Strategy |
|---|---|
| Wake frequency | Hourly tick (cron `0 * * * *`). Most ticks are no-ops. |
| Per-source cadence | Smart polling driven by learned `publishCadenceDays` + `nextExpectedAt`. Default 14d for unseen, narrows to median after 5+ samples. |
| Max sources per cycle | 10. Prevents one slow cycle from holding the lease longer than `maxDurationSeconds`. |
| Concurrency safety | `RunnerLease` unique constraint on `(cycleName, windowKey)`. Hourly window → at-most-once per hour. |
| Retry strategy | Per-doc retry inside the sidecar (3 attempts on network errors, already there). Per-cycle no auto-retry; failed cycles surface in Grafana and require operator intervention with `--window-key=<recovery-key>`. |
| Replay window | Operator runs `tsx scripts/run-cycle.ts --runner=municipal-agenda-ingestion --window-key=replay-2026-05-21-rerun --trigger=replay`. The MarketSourceDoc `@@unique([sourceId, docUrl])` constraint guarantees idempotency — the same doc URL upserts, and `persistSidecarPayload`'s internal dedup prevents duplicate signals. |
| Checkpoint strategy | None needed — each `scrapeOneSource` call is itself idempotent via MarketSourceDoc dedup. Per-source progress is durable; a mid-cycle crash resumes by selecting the same source on the next tick. |
| Duplicate suppression | Multi-layer: (a) `MarketSourceDoc.docUrl` unique per source — won't re-extract; (b) `persistSidecarPayload` skips signals already attached to docs; (c) live-ingestion checks `ProjectSignal` by `(sourceId, sourceKind)` before attaching. |
| Stale detection | (a) `RunnerLease.leaseExpiresAt < now() AND status IN (claimed, running)` → `runner-janitor-hourly` (from O2 plan §10) flips to `stale`. (b) `lastScannedAt < now() - 7d` → forced scrape on next selectDueSources. (c) Three cycles past `nextExpectedAt` with zero new docs → `MarketSource.publishStatus = STALE_PUBLISH` (new optional field), surface in operator workspace. |
| Observability | `runner_cycle{runner=municipal-agenda-ingestion}` events. `neuroglitch_ingestion_processed_total{source_kind, decision}` ticks up per signal. New metric: `neuroglitch_agenda_sources_due` (gauge) — visible "queue depth." New metric: `neuroglitch_agenda_publish_cadence_days{source_id}` (gauge) — see at a glance which sources are healthy. |

## 6. Signal-quality heuristics

The Claude extraction prompt in [routers/market.py](../../sidecar/routers/market.py) (line ~405) already produces structured signals with `signal_subtype`. Filtering happens in two layers:

### 6.1 Sidecar-side (already exists, minor tuning)

- `signal_subtype` enum already covers REZONING, PLAT, SITE_PLAN, SUP_CUP, VARIANCE, COMPREHENSIVE_PLAN, ANNEXATION, TIF, BOND, PERMIT_AWARD, CONTRACT_AWARD, OTHER.
- **Small prompt update needed in O2.2:** add explicit subtypes UTILITY_EXPANSION (sewer, water, lift station, treatment plant), CORRIDOR_STUDY, INFRASTRUCTURE_PLAN, INDUSTRIAL_REZONING. Currently these fall into OTHER and lose specificity.
- Prompt already instructs Claude to assign `relevance_score` (0–100) per signal.

### 6.2 App-side filtering — runs inside `persistSidecarPayload`

Already enforces (via `MarketSource` tuning fields):
- `minRelevanceScore` (default 60) — drops sub-threshold signals.
- `minEstimatedValue` (optional) — drops sub-threshold leads.
- `projectTypeAllowlist` (CSV) — drops disallowed types.

### 6.3 New filters to add in O2.2

| Reject (drop the signal) | Justification |
|---|---|
| `signal_subtype = OTHER` AND `relevance_score < 75` | OTHER without high confidence is almost always ceremonial. |
| Headline matches ceremonial regex: `^(consent|approval of minutes|adjournment|invocation|pledge|recess|public comment|reading of|swearing in|recognition|proclamation)` | Pure procedural noise. |
| Doc title matches ceremonial-meeting regex: `(special meeting cancelled|work session.*budget review|reorganization)` | Whole-doc filter. Saves Claude cost downstream — apply at MarketSourceDoc level pre-extraction. |
| Duplicate signal heuristic: same `headline` substring (≥ 80% overlap) from same source within prior 60 days | Continuance suppression — most "tabled" items reappear verbatim; we want one signal with `nextMeetingDate` set, not 4 separate signals. |

| Prioritize (boost relevance_score by +10, capped at 100) | Justification |
|---|---|
| `signal_subtype IN (UTILITY_EXPANSION, ANNEXATION, CORRIDOR_STUDY, INFRASTRUCTURE_PLAN)` | Strongest leading indicators of development pressure. |
| Headline contains parcel acreage > 5 acres OR project_value > $5M | Material projects only. |
| Developer/owner name appears in ≥ 2 other signals from prior 90 days (recurring-actor boost) | Pattern detection — recurring developer means they're building a pipeline. |
| Site is within 500m of a previously-permitted parcel in MI-7 ParcelPressure snapshots | Spatial clustering — corridor emergence. |

Implementation note: items in §6.3 belong in a small new module [lib/services/marketIntelligence/signalHeuristics.ts](../../lib/services/marketIntelligence/) called from `persistSidecarPayload` before the relevance-floor check. Pure function; unit-testable.

## 8. Replay strategy

The replay-validation infrastructure that O1.6 ships is the substrate; the runner just needs to be replay-safe. It already is, by virtue of:

1. **`MarketSourceDoc.@@unique([sourceId, docUrl])`** — re-running the same scrape against the same listing page upserts existing rows; only genuinely-new docs create new doc rows.
2. **`persistSidecarPayload` internal dedup** — checks for existing MarketSignal rows tied to the same docId before insert. (Note: needs verification in O2.2; the route doesn't show this explicitly. If absent, add a `(sourceDocId, headline_normalized)` uniqueness check.)
3. **`processNewMarketSignal` idempotency** — checks `ProjectSignal` existence by `(sourceId, sourceKind, detachedAt IS NULL)` before attaching ([lib/services/liveIngestion/processSignal.ts](../../lib/services/liveIngestion/processSignal.ts)).
4. **`RunnerLease.windowKey` uniqueness** — replay with `--window-key=replay-<date>-<reason>` bypasses the standard hourly window, so two operators don't accidentally double-replay.

**Replay use cases**:
- Source URL changed, want to re-scrape last 90 days: change `MarketSource.dateFrom`, run with `--window-key=replay-source-X-2026-05-21`.
- Claude prompt was updated, want to re-analyze raw_text already on disk: separate `analyze-only` runner (out of scope for O2.2; lives in MarketDocAnalysis table already).
- Bad batch needs reprocessing: operator deletes ProjectSignal rows for the affected sourceDocIds, runs ingestion replay; the per-doc dedup in step (2) will skip re-extraction but step (3) will re-attach.

## 10. Operational risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Sidecar `/market/scrape-source` times out on a large CivicPlus packet (>500k chars) | Medium | Single source stalls a cycle | Sidecar's Ollama prefilter (`prefilterMode = always`) already handles this when configured. Set `prefilterMode = always` on any source whose first scrape produces a doc > 200k chars. Per-source per-call timeout of 240s; on timeout, mark doc with error and continue to next source. |
| Claude API rate-limit during a wide batch | Low (current scale) | Cycle partial-fails | Sidecar already handles 429 backoff. Cap sources/cycle at 10 (§3.3). |
| Claude cost runaway from a misconfigured source pulling 1000s of docs | Medium | $-figure surprise | (a) `MarketSource.minRelevanceScore` floor; (b) per-cycle max-doc cap inside sidecar; (c) **new metric**: `neuroglitch_agenda_cost_usd_total` — alert at $5/day rate. |
| Live-ingestion bridge throws inside the runner body, halts the cycle | Medium | Lost progress for downstream sources | Wrap each per-source block in try/catch (per §3.2 pseudocode). One source's failure does not poison the cycle. |
| Schema drift: signal subtype "UTILITY_EXPANSION" emitted by Claude but consumer code only knows the legacy enum | Low | Silent drop in projectAggregation | Subtype is `String?` in the schema (no enum constraint). Continuation detector treats unknown subtypes as low-weight match. Acceptable degradation. |
| Duplicate signals from continuance items ("tabled to next meeting") | High | Project signal-count inflation | §6.3 dedup heuristic (headline 80% overlap within 60 days). Also: `MarketSignal.nextMeetingDate` field already exists for the CONTINUED case — use it. |
| Lease starvation if a single source's scrape exceeds `maxDurationSeconds` | Low | Cycle aborts mid-run; next hour resumes | Cap per-source scrape timeout at `maxDurationSeconds / 12` ≈ 275s. Source that consistently exceeds it gets flagged `OPERATOR_REVIEW`. |
| Operator manually triggers `/api/.../scrape` and the runner triggers the same source simultaneously | Low | Two parallel scrapes of one source; doubled cost; possible primary-key conflicts | The HTTP route already serializes per-source via `BackgroundJob` unique constraint for queue-scrape; immediate-scrape route does not. Acceptable transient race because MarketSourceDoc dedup makes the second writer idempotent. **Long-term**: introduce an advisory lock per `sourceId`. Defer. |
| Discovery flow finds a source whose URL is behind Cloudflare / login wall | Medium | Wasted Claude calls returning HTML challenge pages | Detect by `raw_text` starting with `<!DOCTYPE html>` AND containing "challenge" or "cloudflare" — mark doc with error, do not pass to Claude. Add as filter in §6.3. |
| Per-source `nextExpectedAt` math goes wrong (e.g., one bad doc date) | Medium | Source scraped daily or never | Cap `publishCadenceDays` to [1, 60]. Re-derive only when `cadenceSampleSize >= 5`. |
| Replay validation breaks because runner's persistence path differs from the HTTP route's | Medium | O1.6 CI failure | Extract scrape body to shared function (§7.1) so both share one code path. Single source of truth. |
